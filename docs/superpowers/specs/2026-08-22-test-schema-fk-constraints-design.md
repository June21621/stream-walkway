# 테스트 스키마에 실제 제약(FK/UNIQUE) 도입 설계

**작성일:** 2026-08-22
**브랜치:** `test-schema-fk-constraints`
**기준 커밋:** `77b507c`

## 배경

`services/writer/src/test/resources/schema.sql`과 `services/reader/src/test/resources/schema.sql`에는 `captures` 테이블 하나만 있고 FK가 전혀 없다. 그래서 **이 저장소의 어떤 자동화 테스트도 진짜 FK 위반을 만들 수 없다.**

이것이 직전 버그(존재하지 않는 `stream_id`로 Trail 생성 시 500)가 유닛 테스트 176개를 모두 통과하면서도 Docker 실기동에서야 드러난 구조적 원인이다. 그 버그를 고치며 추가한 `TrailCommandHandler`의 FK catch 분기는 지금 **손으로 쓴 가짜 예외 메시지로만** 테스트된다.

## 목표

1. `TrailCommandHandler`의 FK 분기(`trails_stream_id_fkey` 매칭)를 진짜 제약 위반으로 검증한다.
2. UNIQUE(`stream_id`, `camera_number`) → 409 경로도 진짜 제약 위반으로 검증한다.
3. 테스트 스키마를 운영 스키마(`infra/scripts/init-db.sql`)와 정렬해 드리프트를 줄인다.

## 계획 수립 전 실측으로 확인한 사실 (추측 아님)

H2 2.3.232에 직접 JDBC로 붙이고, `@DataJpaTest`를 실제로 돌리고, `postgis/postgis:15-3.3-alpine` 컨테이너에 운영 `init-db.sql`을 그대로 적용해서 확인했다.

### 1. H2는 PostGIS 없이 GEOMETRY를 네이티브 지원한다 — 우려했던 난관이 아니다

- `GEOMETRY(POINT, 4326)` / `GEOMETRY(LINESTRING, 4326)` 컬럼 생성 성공.
- subtype과 SRID를 실제로 강제한다: POINT 컬럼에 LINESTRING을 넣거나 SRID 3857을 넣으면 `22018` 데이터 변환 에러가 난다.
- 값은 `org.locationtech.jts.geom.Point`로 그대로 읽힌다.
- `@DataJpaTest`에서 `Stream`(LineString)/`Trail`(Point) 엔티티가 SRID 4326을 유지한 채 저장·재조회됐다. Hibernate Spatial + H2 조합이 별도 설정 없이 동작한다.

즉 **Testcontainers는 GEOMETRY 때문에 필요한 게 아니다.** 아래 3번 때문에 필요하다.

### 2. ddl-auto none이 테스트에도 적용된다 → schema.sql이 유일한 스키마 소스다

`services/writer/src/main/resources/application.yaml`의 `spring.jpa.hibernate.ddl-auto: none`이 `@DataJpaTest`에서도 그대로 유효한 걸 `Environment`로 확인했다(출력값 `none`). Hibernate가 테이블을 만들지 않으므로 `schema.sql`에 없는 테이블은 존재하지 않는다. 이것이 `streams`/`trails`가 테스트 DB에 아예 없었던 이유다.

### 3. 제약 위반 에러 문자열이 H2와 Postgres에서 다르다 — 이번 작업의 진짜 관문

| 항목 | H2 2.3.232 | PostGIS 15.4 (운영) |
|---|---|---|
| FK 위반 메시지 | `Referential integrity constraint violation: "TRAILS_STREAM_ID_FKEY: PUBLIC.TRAILS FOREIGN KEY(STREAM_ID) REFERENCES PUBLIC.STREAMS(ID) (999999)"` | `ERROR: insert or update on table "trails" violates foreign key constraint "trails_stream_id_fkey"` |
| UNIQUE 위반 메시지 | `Unique index or primary key violation: "PUBLIC.TRAILS_STREAM_ID_CAMERA_NUMBER_KEY_INDEX_9 ON PUBLIC.TRAILS(...)"` | `ERROR: duplicate key value violates unique constraint "trails_stream_id_camera_number_key"` |
| SQLState (FK) | `23506` | `23503` |
| SQLState (UNIQUE) | `23505` | `23505` |

핵심 귀결:

- 현재 핸들러의 `message.contains("trails_stream_id_fkey")`는 **Postgres에서 true** 다. 이번에 `pg_constraint` 조회가 아니라 실제 던져진 예외 메시지로 직접 확인했다.
- 같은 코드가 **H2에서는 false** 다. H2가 식별자를 대문자로 출력하기 때문이다.
- H2의 UNIQUE 메시지는 제약 이름이 아니라 **인덱스 이름**(`..._KEY_INDEX_9`)을 담는다. 뒤의 숫자는 H2 내부 객체 카운터라 **불안정하다 — 테스트에서 이 문자열을 단언하면 안 된다.**

### 4. Hibernate의 getConstraintName()은 H2에서 신뢰할 수 없다

`org.hibernate.exception.ConstraintViolationException.getConstraintName()`이 H2에서 **`RAILS_STREAM_ID_FKEY`** 를 돌려준다. 앞 글자 `T`가 잘린다(Hibernate의 H2 제약명 추출기 버그). Spring이 감싼 `DataIntegrityViolationException` 메시지의 `constraint [...]` 부분에도 같은 잘린 값이 들어간다. 또 FK 위반인데 `getKind()`가 `OTHER`로 나온다.

따라서 **"문자열 매칭을 버리고 getConstraintName() API로 갈아탄다"는 선택지는 성립하지 않는다.** Postgres 쪽 `PSQLException.getServerErrorMessage().getConstraint()`는 `trails_stream_id_fkey`를 정확히 주지만, 그건 Postgres 전용이다.

### 5. TIMESTAMP → TIMESTAMPTZ 정렬은 버그 수정이 아니라 스키마 충실도 문제다

JVM 기본 시간대가 `Asia/Seoul`인 상태에서 `captures.created_at`이 지금처럼 `TIMESTAMP`여도 `Instant`가 **drift 0으로 정확히 왕복**한다(실측). 운영 Postgres에서 관찰됐던 시간 밀림이 H2에서는 재현되지 않는다.

그래도 정렬한다. H2는 `TIMESTAMP WITH TIME ZONE`을 지원하고(`OffsetDateTime`으로 반환) 운영 스키마와 같아지므로, 정렬 비용이 사실상 0이고 드리프트 한 종류가 사라진다.

### 6. ON DELETE CASCADE는 H2에서도 동작한다

`streams` 행을 지우면 참조하던 `trails` 행이 함께 사라지는 걸 확인했다.

### 7. 변경 영향 범위는 좁다

- DB를 실제로 건드리는 테스트는 writer/reader의 `CaptureRepositoryTest` 2개뿐이다.
- 컨트롤러 테스트는 전부 `@WebMvcTest`라 영향이 없다.
- H2의 `GENERATED BY DEFAULT AS IDENTITY`는 명시적 `id` 값을 받는다(실측). 시드 데이터를 고정 id로 넣을 수 있다.

### 8. 실행 환경

- 이 저장소에 **CI 설정이 없다**(`.github` 없음). Java 모듈은 `package.json`이 없어 turbo `test` 파이프라인에도 안 들어간다. 테스트는 사람이 `./mvnw test`를 직접 돌릴 때만 실행된다.
- Docker가 떠 있고 `postgis/postgis:15-3.3-alpine` 이미지가 로컬에 있다(pull 시간 0).
- Spring Boot 3.5.1이 Testcontainers **1.21.2**를 관리한다. 해당 버전 `org.testcontainers:junit-jupiter`에 `EnabledIfDockerAvailable` 클래스가 실재하는 걸 jar 목록으로 확인했다.
- writer `pom.xml`의 JaCoCo는 `prepare-agent`(기본 argLine) + `report`(`test` 단계) 구성이라 **surefire에 묶여 있다.**

## 설계

### 1. 테스트 스키마 (writer / reader 각각 schema.sql, 동일 내용 2벌)

운영 `init-db.sql`과 같은 구조·같은 제약 이름으로 `streams` → `trails` → `captures` 순서로 작성한다.

**제약 이름을 명시적으로 지정하는 것이 핵심이다.** H2가 자동 생성하게 두면 `CONSTRAINT_A67` 같은 이름이 나와서(실측) 아무것도 검증할 수 없다. Postgres가 자동 생성하는 이름(`trails_stream_id_fkey`, `trails_stream_id_camera_number_key`, `trails_status_check`)을 `CONSTRAINT <name>` 절로 명시한다.

포함:

- `streams`: PK, `location GEOMETRY(LINESTRING, 4326) NOT NULL`, `created_at TIMESTAMP WITH TIME ZONE`
- `trails`: PK, `trails_stream_id_fkey`(FK → `streams(id)` ON DELETE CASCADE), `trails_stream_id_camera_number_key`(UNIQUE), `trails_status_check`(CHECK), `location GEOMETRY(POINT, 4326) NOT NULL`, `created_at TIMESTAMP WITH TIME ZONE`
- `captures`: PK, `captures_trail_id_fkey`, `captures_stream_id_fkey`(둘 다 ON DELETE CASCADE), `created_at`/`updated_at TIMESTAMP WITH TIME ZONE`

H2에 옮기지 않는 것과 그 이유를 파일 주석으로 남긴다:

- PostGIS extension — H2는 GEOMETRY를 네이티브 지원하므로 불필요
- `update_updated_at_column()` 트리거 — plpgsql 없음. `updated_at` 컬럼은 두되 자동 갱신되지 않음
- 성능 인덱스 — 테스트에서 의미 없음

**미확정 항목:** `road_status` CHECK는 한글 리터럴이라 H2에서 인코딩 문제가 날 수 있다. 구현 중 실측하고, 깨지면 그 CHECK만 제외하고 이유를 주석으로 남긴다. 기존 `CaptureRepositoryTest`가 해당 한글 값을 쓰므로 문제가 있으면 즉시 드러난다.

### 2. 핸들러 매칭을 대소문자 무시로

`TrailCommandHandler`의 두 `contains` 비교를 대소문자 무시로 바꾼다. SQL 식별자는 원래 대소문자를 구분하지 않으므로 프로덕션 코드로서도 옳고, H2와 Postgres 양쪽에서 같은 동작이 된다. 이게 있어야 H2 테스트가 분기를 실제로 태울 수 있다.

검증된 매칭 안전성:

- H2 FK 메시지는 `TRAILS_STREAM_ID_FKEY`를 담고 `TRAILS_STREAM_ID_CAMERA_NUMBER_KEY`는 담지 않는다.
- H2 UNIQUE 메시지는 `TRAILS_STREAM_ID_CAMERA_NUMBER_KEY`를 담는다(뒤에 `_INDEX_9`가 붙지만 `contains`이므로 무관).
- 따라서 핸들러의 UNIQUE-먼저 검사 순서가 두 엔진 모두에서 안전하다.

### 3. 검증 테스트 2층

**H2 층** (빠름, 항상 실행) — writer에 신규 `@DataJpaTest`:

- 리포지토리 수준: 없는 `stream_id`로 `Trail` 저장 시 `DataIntegrityViolationException`이 실제로 난다
- 리포지토리 수준: 같은 `(stream_id, camera_number)` 중복 저장 시 위반이 실제로 난다
- 핸들러 수준: 진짜 FK 위반 → `IllegalArgumentException`(400 경로)
- 핸들러 수준: 진짜 UNIQUE 위반 → `DuplicateTrailException`(409 경로)
- `Stream`/`Trail` geometry가 SRID 4326을 유지한 채 왕복
- `ON DELETE CASCADE` 동작
- `created_at`이 `TIMESTAMPTZ` 컬럼에서 UTC로 정확히 왕복

**H2 에러 문자열 자체는 절대 단언하지 않는다** — `..._INDEX_9`의 숫자 접미사가 불안정하기 때문이다. 예외 타입과 동작만 검증한다.

**Postgres 층** (Testcontainers, `postgis/postgis:15-3.3-alpine`) — writer에 신규 테스트:

- 컨테이너에 **운영 `init-db.sql`을 그대로 주입**한다. 손으로 옮겨 적은 스키마가 아니라 실제 운영 스키마 위에서 검증하므로 드리프트가 원천 차단된다.
- 같은 두 분기를 **실제 Postgres 에러 문자열**로 검증한다. 이것이 목표 1의 진짜 답이다.
- 컨테이너는 `static`으로 클래스당 1회만 띄운다.

**FK 분기를 태우는 방법 (H2 층과 Postgres 층에 공통 적용):** 핸들러는 `save()` 전에 `streamRepository.existsById()`로 선체크를 하므로, 그냥 없는 id를 주면 FK까지 도달하지 못하고 선체크에서 걸린다. FK catch 분기를 태우려면 **`StreamRepository`만 Mockito mock으로 `existsById → true` 고정하고 `TrailRepository`는 진짜 DB에 붙인 핸들러 인스턴스**를 만들어야 한다. 이는 핸들러 주석이 말하는 "존재 확인과 저장 사이에 하천이 삭제되는 경쟁에서 진 경우"를 그대로 재현하는 것이라 의미도 정확하다.

UNIQUE 분기는 이 우회가 필요 없다. 실제로 존재하는 하천에 같은 `camera_number`를 두 번 넣으면 선체크를 정상 통과한 뒤 UNIQUE 위반에 도달한다.

**Testcontainers 초기화 스크립트 주의점:** 운영 `init-db.sql`에는 `$$ ... $$`로 감싼 plpgsql 함수 본문이 있다. Testcontainers의 `withInitScript`는 내부적으로 세미콜론 기준 문장 분리를 하므로 이 블록에서 깨질 수 있다. 파일 전체를 하나의 `Statement.execute()`로 넘기면 문제없이 적용되는 것은 이미 실측으로 확인했다(probe에서 성공). 구현 시 `withInitScript`를 먼저 시도하고, 깨지면 `@BeforeAll`에서 파일을 통째로 읽어 단일 statement로 실행하는 방식으로 전환한다.

### 4. 실행 단계: surefire test

Testcontainers 테스트를 `*Test` 이름으로 짓고 기본 `test` 단계에서 돌린다. Docker가 없으면 `@EnabledIfDockerAvailable`로 skip한다(실패가 아니라 리포트에 보이는 skip).

**이 저장소에 CI가 없다는 것이 결정적 근거다.** 기본 실행 경로에서 빠지는 테스트는 여기선 사실상 "안 돌아가는 테스트"가 된다. 이번 작업의 취지가 정확히 "테스트가 못 잡는 사각지대 제거"인데, 검증을 `verify`/프로파일/태그 같은 opt-in 경로에 두면 같은 함정을 새로 파는 셈이다. 직전 버그도 "유닛 테스트 176개 통과 + 사람이 기억해서 하는 Docker 실기동에서야 발견"이었다.

부수 효과로 pom 설정 추가가 0이고, JaCoCo(surefire에 묶여 있음)가 FK/UNIQUE 분기 커버리지를 그대로 잡는다.

의존성은 `services/writer/pom.xml`에 `org.testcontainers:postgresql`, `org.testcontainers:junit-jupiter` 둘만 `test` 스코프로 추가한다. 버전은 Spring Boot parent가 관리한다.

### 5. 기존 CaptureRepositoryTest 2개 (writer / reader)

`captures`에 FK가 생기면 지금처럼 `trailId=1` 고아 행을 넣을 수 없다. `@BeforeEach`에서 native insert로 `streams(id 1,2)` / `trails(id 1,2,3)` 시드를 **명시적 id로** 넣는다. H2의 `GENERATED BY DEFAULT AS IDENTITY`가 명시 id를 받는 걸 실측했으므로, 기존 테스트 본문의 하드코딩된 `1,2,3`을 손대지 않아도 된다. 테스트 개수도 유지된다.

시드 insert에는 `location`이 `NOT NULL`이므로 geometry 리터럴이 필요하다. H2는 `'SRID=4326;POINT(126.97 37.55)'` / `'SRID=4326;LINESTRING(126.97 37.55, 126.98 37.56)'` 형태의 EWKT 문자열을 받는다(실측).

명시적 id 시드는 IDENTITY 시퀀스를 앞당기지 않으므로, 같은 테스트 클래스에서 `streams`/`trails`를 자동 생성 id로 추가로 만들면 충돌할 수 있다. `CaptureRepositoryTest`는 `captures`만 새로 만들므로 해당 사항이 없다. 새 제약 검증 테스트는 시드를 쓰지 않고 엔티티로 직접 생성하는 방식으로 분리해 이 문제를 피한다.

덤으로 `created_at` 검증을 `isNotNull()`에서 **저장 전후 시각 구간 안에 있는지** 확인하는 쪽으로 강화한다. 지금 형태로는 타임존이 어긋나도 통과하기 때문이다.

### 6. reader 범위

reader엔 커맨드 핸들러가 없고 DB를 쓰는 건 `CaptureRepositoryTest`뿐이다. 스키마만 writer와 동일하게 동기화하고, 제약 검증 테스트와 Testcontainers는 writer에만 둔다.

### 7. 스키마 중복 관리

`schema.sql`을 writer/reader 두 벌로 복사 유지한다. 모듈 독립성이 유지되고 Maven 설정 변경이 없다. 드리프트 위험은 있지만, Testcontainers 테스트가 운영 `init-db.sql`을 직접 사용하므로 진짜 기준선은 따로 지켜진다.
